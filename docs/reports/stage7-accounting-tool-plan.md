既存機能の状態について気づいた点（問題の評価つき）：

1. **画像は長辺2,000pxに縮小してからOCRする**（`ocr.ts` の `MAX_OCR_DIMENSION`）。細長いレシートの写真では、幅が数百pxになり、小さな文字が読めなくなる可能性がある（推測。実測は未実施）。影響：精度。対応案：領収書専用の縮小ルール（幅を基準にするなど）を、実物の評価（11章）の結果で決める。既存のOCRツールの挙動は変えない。
2. 単語ごとの位置を返す関数 `recognizeImageWithWords` が受け付けるページ分割モードは `"6"` のみ。領収書向けの設定は、評価の結果を見て、小さな拡張が必要になる可能性がある（影響：小）。
3. iPhoneのHEIC形式の写真の扱いは、既存のOCRがJPG・PNG・WebPのみのため、未確認（影響：中。スマートフォン利用が前提のため、評価時に確認する）。

### 初期リリースの推奨仕様（提案）

1. 画像（JPG・PNG・WebP）とPDFを複数読み込む。HEICは未対応と表示する（未確認事項の確認後に再判断）。
2. PDFは、文字情報のあるページは文字をそのまま使い、無いページだけOCRする。
3. 1書類（1画像、またはPDFの1ページ）につき、**日付・取引先・合計金額（税込）**を抽出する。ほかに、読み取れた税率（8%・10%）の手がかりを、参考として表示する（値を確定させない）。
4. 確認画面は、1行＝1書類の表。元の画像を横に拡大表示し、値を修正できる。信頼度が低い、または確定できなかった値は「要確認」で目立たせる。**確認済みにした行だけを出力する。**
5. 勘定科目・税区分・決済の扱い（決済口座名を入力すると決済済みとして出力、空欄なら未決済）は、**利用者が選ぶ。ツールは自動判定しない。**勘定科目と税区分は、全行の既定値と行ごとの個別指定を用意する。
6. 税率が混在するレシートは、1行を複製して分割する（金額は利用者が入力）。自動分割はしない。
7. 出力は、まず「汎用CSV」（日付・取引先・金額・勘定科目・税区分・備考。Excelで開ける形式）。会計ソフトの取り込み形式は、公式サンプルとの照合後に追加する。
8. 通常の操作にログイン、AI、サーバーとの通信は不要。データは画面を閉じると消える。保存は行わない。
9. 説明文に「読み取り結果は必ず確認してください」「会計・税務の助言ではありません」「電子帳簿保存法に対応した保存の仕組みではありません」を表示する。

### 初期リリースから除外するもの

AIによる読み取り、Excel出力、証憑の保存・整理用のPDF・ZIP、設定の保存、会計ソフトの複数対応、勘定科目・税区分の自動判定、インボイス制度の要件判定、税率混在の自動分割、請求書（取引先からの請求）の項目抽出の作り込み、アカウント連携・課金の追加。

請求書は、入力としては読み込めるが、日付・取引先・合計の抽出ルールは領収書・レシートを主な対象とし、請求書専用の調整は初版では行わない（形式が多様で、ルールが膨らむため）。

## 6. 対応する会計ソフトと、その選定理由

### 選定：freee会計（取引・口座振替のインポート）

理由：

1. 領収書・レシートは「1枚＝1件の支出」であり、freeeの取引インポートの形（収支区分・発生日・勘定科目・税区分・金額）にそのまま対応する。弥生は、借方・貸方の仕訳の形（27列）で、1件の支出でも借方・貸方の科目と税区分の記述形式を組み立てる必要があり、初版の実装と確認の負担が大きい。
2. 公式ページで、必須項目、日付形式、サイズ上限、取り消し方法（7章）が確認できた。
3. 工程6でもfreeeを最初の対応先としていた（引き継ぎ）。

選定しなかったソフトの状況（公式ページの取得結果）：

| ソフト | 確認できたこと | 確認できなかったこと |
|---|---|---|
| 弥生（弥生会計 オンライン・やよいの青色申告 オンライン） | 「弥生データのインポート」で、27列の仕様、必須列、識別フラグ、日付・金額の形式、Shift-JISのみ、1.0MBまで・1,000行まで、税区分の記述形式（例：「課対仕入内10%」）まで公式に記載あり | ヘッダー行の有無、勘定科目名が登録名と完全一致する必要があるか。デスクトップ版の仕様は読んでいない |
| マネーフォワード クラウド会計 | 「取引明細のインポート」で、入力必須は日付と入金/出金、勘定科目などは登録済みの名称と一致が必要、重複チェックなし | 列名・列順、日付・金額の形式、文字コード、サイズ上限、税区分の記述。**CSVとして取り込む公式の列仕様は見つけられなかった** |

弥生は、仕様が公開されているため、**2番目の対応先の候補**（需要が確認できてから。初版では対応しない）。マネーフォワードは、仕様を確認できるまで計画に入れない。

| 文字コード（UTF-8、Shift-JIS、BOMの要否） | CSVを文字化けなしで取り込めるか | freeeの取り込み画面から公式サンプルCSVを取得し（**ダウンロードは利用者が実施**）、文字コードを確認。テスト用事業所で取り込む |
| 列の順序が固定か、列名で判断するか、任意の列を省略してよいか | CSVの組み立て方 | 公式サンプルとの照合、テスト取り込み |
| 勘定科目・税区分・取引先がfreeeの登録名と一致する必要があるか、未登録の場合の挙動 | 名称が違ったときのエラーや自動作成 | テスト用事業所での取り込み |
| 税区分の正式な名称の例（「課対仕入10%」など） | 利用者が選ぶ税区分の候補表示 | 公式サンプル、取り込み画面の選択肢 |
| 金額の形式（カンマ、マイナス、税込・税抜の扱い） | 金額列の仕様 | 公式サンプル、テスト取り込み |
| 引用符つきの値（カンマや改行を含む取引先名など）の取り込み | 取引先名にカンマを含む場合 | テスト取り込み |
| この機能を使えるプラン（個人事業主・法人、プラン別） | 対象となる利用者の範囲 | freeeの公式ページ・利用者のプランの画面 |
| 数式として解釈される値（`=` 等で始まる取引先名）の取り扱い | 数式対策の方法（10章） | テスト取り込み |
| 日付の0埋めの要否（`2026/1/5` と `2026/01/05`） | 日付の出力形式 | 公式サンプル、テスト取り込み |

**以上の未確認事項が確認できるまで、freee形式のCSVを「freeeに取り込めます」と表示しない。** 初版（工程8）は汎用CSVとし、freee形式は公式サンプルとの照合・テスト取り込みの後（工程10）に「対応」とする。

## 8. OCR・PDF処理・CSV出力の実装案

### 8-1. 処理の流れ（提案）

```
読み込み（画像／PDF）
  → ファイルの種類・サイズ・ページ数の確認（既存の上限を再利用）
  → PDFのページ：文字情報あり → 文字を取り出す（OCRしない）／なし → 画像化してOCR
  → 画像：領収書向けの縮小（幅を基準にする案。実物の評価で決める）→ OCR
  → 文字列と単語の位置・信頼度 → 抽出規則（日付・合計金額・取引先）
  → 確定できない値は空にして、候補と理由を持たせる（推測値を確定値にしない）
  → 確認・修正画面 → 確認済みの行だけをCSVへ
```

### 8-2. 処理方式ごとの整理

| 区分 | 方式 | 精度 | プライバシー | 費用 | 判断 |
|---|---|---|---|---|---|
| ブラウザ内OCR | 既存のtesseract.js（高速・量子化モデル） | **未測定**（領収書では不安定になりうるという推測。精度は実物の評価で確かめる） | ブラウザ内 | サイトの配信量のみ | 初版の主方式 |
| テキストを持つPDFからの抽出 | 既存のpdfjsの文字取り出し | 文字情報があれば正確（原理上。領収書PDFでの実測は未実施） | ブラウザ内 | なし | 初版に含める。OCRより優先 |
| スキャンPDF・画像 | 画像化してブラウザ内OCR | 画像の品質に左右される（実測は未実施） | ブラウザ内 | なし | 初版に含める。確認・修正を前提にする |
| 外部AI（画像・文字を送信） | 既存のAI補助の仕組みを拡張 | 未検証 | 領収書の画像・文字が外部へ送信される | 9章 | 初版は含めない |

### 8-3. 抽出規則の設計方針（提案）

- 日付：西暦（`/` `-` `.` 区切り、「年月日」）、令和などの和暦。「支払期限」「有効期限」などの語がある行は取引日にしない。複数あって判断できなければ空にして、候補を見せる。
- 合計金額：「合計」「お支払」「ご請求額」などの語の近くを優先。「小計」「税」「預り」「お釣り」の行は除外。候補が複数なら空にして、候補を見せる。桁区切りのカンマがOCRで別の記号に読まれる誤読への対応を含める。
- 取引先：書類の上部にある、会社名・店名らしい行。電話番号・住所・宛名・書類名は除外。
- 信頼度：単語ごとの信頼度が低い値は「要確認」とする。**閾値は、実物の評価の結果で決める**（今回は決めない）。
- 規則は純粋な関数として作り、OCRの結果を模した文字列でテストできるようにする（OCRの結果が環境で変わっても、規則のテストが安定するように）。
- 確定できなければ空にする設計を優先し、誤った値が自動で入ることを避ける。ただし、これで誤った値が全く出ないことは保証できない（誤読が別の有効な値に見える場合）。

### 8-4. CSV出力の方針（提案）

- 汎用CSV（初版）：UTF-8（BOM付き）、日付はYYYY/MM/DD、金額は整数。列は、日付・取引先・金額（税込）・勘定科目・税区分・備考。BOM付きは、Excelで開くときの文字化けを避けるため（既存のCSV出力と同じ方式）。
- freee形式（工程10）：7章の未確認事項を確認してから、列・文字コード・日付の形式を確定する。確認前は実装しない。
- 共通：金額が1円未満・非整数・極端な桁の行、存在しない日付、取引先の長さ超過は、出力せずに理由を表示。ファイルサイズが5MBを超える場合は、出力しない。
- 数式対策は10章。

## 9. AIを利用する場合と利用しない場合の比較

### 判断：初版はAIを使わない。使うかどうかは、実物の評価の結果で決める。

| 観点 | AIなし（初版の案） | AI補助を追加する場合（任意・プレミアム限定の案） |
|---|---|---|
| 処理 | ブラウザ内OCR＋規則＋利用者の確認 | 既存のAI補助の仕組みに、領収書向けの読み取りを追加 |
| 精度 | 未測定。誤読は確認・修正で補う | 未検証。画像を直接読むため向上する可能性（推測）。ただし、誤りが無くなるわけではない |
| 送信されるデータ | なし（外部への送信なし） | 領収書の縮小画像（既存の上限：1回4枚まで、合計2.6MB以下）。画像には、氏名・住所・電話番号・カード番号の一部などが写る可能性がある |
| プライバシー | 現行の説明のまま（ブラウザ内で完結） | 実行ごとの同意、送信内容の画面表示（既存の仕組み）。OpenAI側で、不正利用の監視のため最長30日の記録が保持されうる（プライバシーポリシーの記載）。**領収書全体の画像を送ることになり、現行のAI補助より影響が大きい** |
| 費用 | サイトの配信量のみ | 下の概算 |
| 利用量の制限 | 不要 | 既存の利用枠（期間あたり3.00ドル）に連動 |
| 追加の実装 | なし | 領収書用の読み取り目的の追加、同意文の更新、サーバー側の検証（出力の検証）、APIの変更、テスト、プライバシーポリシー・説明文の更新 |
| プランとの整合 | 全員（現在は全ツールがスタンダード扱い） | プレミアム限定（既存のAI補助と同じ） |
| 初版の前提にしてよいか | はい | **いいえ。** AIを前提に実装しない |

### AI補助の費用の概算（Claudeの計算。仮定を含む）

既存コードの値：単価表（2026-10-22時点）は、標準モデル（gpt-6-luna）が入力 $0.10／出力 $0.50（100万トークンあたり）、高精度モデル（gpt-6.1-sol）が入力 $2.00／出力 $10.00。画像1枚の入力トークンは、コード内の安全側の固定値 6,000 を使う。出力は、仮に300トークンとする（**仮定。実測は未実施**）。為替は、コードの固定値 165円/ドル。

- 標準モデル：約 $0.00075/枚 ≒ 0.12円/枚。期間の上限 $3.00 では、約4,000枚分（概算）。
- 高精度モデル：約 $0.015/枚 ≒ 2.5円/枚。期間の上限 $3.00 では、約200枚分（概算）。

実際のトークン数は未測定のため、上記は目安にとどまる。AIを導入する場合は、導入前に実測する。

### AIを検討する条件（提案）

実物の評価で、ブラウザ内OCR＋規則の精度が実用に足りない項目（例：感熱紙の薄い印字、斜め撮影）が確認され、その改善にAIが必要と判断できる場合に限り、別工程として検討する。その際は、同意文・プライバシーポリシー・利用枠・費用の設計を先に行う。

## 10. セキュリティ・プライバシー上の注意点

| 論点 | 方針（提案）と、コードで確認した現状 |
|---|---|
| ファイル内容の送信 | しない。ツールは `processor: "browser"`。CSPの `connect-src` は自サイト・ログイン基盤・広告のドメインのみ。通信の監視テスト（`network-guard.ts`）で、画像・PDFの内容が自社API・外部へ送信されないことを確認するテストを追加する |

| 削除方法 | 行の削除、全消去（リセット）ボタン。出力済みのCSVは利用者の端末に保存されるため、取り扱いは利用者に委ねられることを説明に書く |
| 離脱時 | 未出力の確認済みデータがある場合は、ブラウザの離脱警告（既存の部品） |
| 外部API | 初版は使わない。使う場合は、送信対象と送信先を実行前に画面に表示する（9章） |
| CSVの数式対策 | 取引先名・備考などが `=` `+` `-` `@`（および先頭のタブ・復帰）で始まる場合の扱いを決める必要がある。**汎用CSV（Excelで開く用途）**：既存の座席表と同じく先頭に `'` を付ける。**会計ソフト形式（freee）**：`'` を付けると、取り込んだ取引先名に `'` が残る可能性がある（未確認）。このため、freee形式では、該当する値を確認画面で警告し、利用者に修正してもらう方式を第一案とする。テストで、各パターンを確認する |
| 広告 | 現在、広告機能はオフ（`PRODUCTION_FLAGS.ads = false`）。CSPには広告のドメインが許可されている。広告を再開した場合、領収書を扱う画面に広告のスクリプトが読み込まれるのは、「ブラウザ内で完結する」という説明と相性が悪い（推測）。**この画面には広告枠を置かない**ことを、実装前に決める（12章） |
| エラー時の露出 | OCRの失敗・形式エラーは、ファイル名のみを必要最小限で表示するか、番号（何件目）で示す。ファイル名には個人情報が含まれうるため、表示・出力・ログでの扱いを決める（備考欄に自動でファイル名を入れない） |
| 電子帳簿保存法 | このツールは、情報の整理とCSV作成のためのもので、保存の仕組みではない。国税庁の資料の要件（タイムスタンプ、訂正・削除の履歴、検索機能など）を満たすことは行わず、「対応」「準拠」といった表現を使わない（画面・SEO・説明文）。法令要件の個別の判断は、本報告書では行わない（工程6の整理を引き継ぐ。今回、国税庁の資料は再取得していない） |
| 商標・表示 | 「freee」の表記は、取り込み先の名前としての記述にとどめ、ロゴ・公式を連想させる表現を使わない（利用条件の詳細は未確認） |
| プライバシーポリシー | AIを使わない初版は、現行の記載（OCRを含むツールの処理はブラウザ内）と矛盾しない（コードで確認）。AIを追加する場合、または広告の扱いを変える場合は、改定が必要 |

既存のセキュリティ設計の変更：**初版では変更しない**（CSP、認証、課金、プライバシーポリシーは現状のまま）。

## Claudeの意見

1. **公開を急がず、工程9（実物の評価）を必ず先に行うのが妥当。** OCRの精度は、規則やUIをどれだけ作り込んでも、実物で測るまで分からない。工程8で画面まで作ってから、精度が足りないと分かる可能性はある。その場合も、確認・修正の画面、CSV出力、PDF文字抽出は無駄にならないが、方向転換（前処理の追加、AI補助の検討、対象を電子レシート・PDFに絞る）の判断が必要になる。
2. **freee形式は、最初から「対応」と書かない。** 公式ページに文字コードや列順の記載が無く、手元の情報だけで形式を決めると、取り込めないCSVを「対応」と表示するリスクがある。公式サンプルの照合とテスト用事業所での取り込み（利用者の作業）を、工程10の前提にした。
3. **「確認済みの行だけ出力」は、手間とのトレードオフ。** 件数が多いと面倒になるが、会計データの誤りが直接の損害になるため、初版はこの仕様を推奨する。使われ方を見て、緩める余地はある。
4. **既存の会計ソフトに標準のレシート読み取りがある**（工程6で確認）ため、競合と正面から比べるのではなく、「契約前・契約せずに使える」「ファイルを外へ送らない」という立ち位置が現実的。後者は、広告を再開した場合の画面の扱い次第で崩れるため、この画面に広告枠を置かない決定を勧める。
5. **別プロジェクトの存在に関する補足。** 今回の指示に従い、別プロジェクトの情報は一切使っていない。過去の報告書にその情報を前提とした記述が残っている（工程1・2・6）ため、今後の工程でも、Mr.Satto内の情報だけで判断するときは、報告書の記述をそのまま引用せず、コードで確かめることを勧める。
