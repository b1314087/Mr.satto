## 0. この報告書の読み方

### 0.1 根拠の区分

本書のすべての記述は、次のいずれかの印を付けて区別する。

- 【実測】サービスの実際の利用データから得た数値。**今回は1件も取得できていない**（理由は 0.3）。
- 【事実】ソースコード・テスト・文書・外部ページを実際に読んで確認できたこと。
- 【推定】事実を材料にした Claude の見立て。需要・工数・収益に関するものはすべてここに入る。
- 【未確認】確認する手段がなかった、または確認していない事項。推測で埋めていない。

### 0.2 調査の対象と作業コピー

- 調査したのは、クラウド側の作業コピー（Gitなし）。以前の検証で、Macの正本とソースが一致していることを確認した上で使っている。
- Macの正本では、メンテナンス作業（README書き直し、未使用コードの削除など15ファイル）が**未コミットのまま残っている**。本書はそれらを上書き・破棄していない。本書の追加ファイルは1つだけ。
- ツール数は現在のソースから数えた値（111件）で、`current-state-assessment.md` の「106ツール」とは異なる。同書の作成後にツールが増えたため。同書の「AI機能は年度カレンダーの1つだけ」という記述も、現在は古い（本書 4.1 参照）。

### 0.3 実測データが無い理由【事実】

- 来訪数の計測（`/api/analytics/visit`）は、Cookieを使わない日次のハッシュ化した訪問者数とページビュー合計だけを保存する。**ツール別・ページ別の記録は保存しない**設計。
- 管理画面 `/admin/usage` が読むのは、旧仕様の `tool_usage_daily` だけ。現在の仕様ではツール別の使用回数は記録されない。
- プライバシーポリシーは外部の解析サービスを使わないと明記し、CSPの `connect-src` も自サイト・Supabase・広告配信元に限っている。
- 本番のSupabase・Google Search Console・Vercelの分析画面は、調査の範囲外（本番データへは触れない）。Search Consoleの検索クエリや表示回数は、利用者本人に画面で確認してもらう必要がある【未確認】。

このため「どのツールが実際に使われているか」は**計測できていない**。第2項の上位10件はすべて【推定】であり、需要順位として確定してはいけない。

## 4. AIを導入すべき候補・すべきでない候補

### 4.1 既に実装済みのAI機能（重複して計画しない）【事実】

| 機能 | 入口 | API | 送るもの |
|---|---|---|---|
| カレンダーの予定表読み取り（文字） | fiscal-calendar | `/api/ai/calendar-assist` | 予定表のセルの文字（上限: 100行×12列、入力約12万バイト） |

- ログは `console.info("[ai]", …)` で内容を含めない。画面には金額を出さず「AIトークン」で表示する。
- `current-state-assessment.md` はAIを「年度カレンダーの1つだけ」と書いているが、現在は上の4機能（入口は4ツール）。【事実】
- 実際のAPIでの精度・実費の測定（コード内で「工程4F」と呼ばれている項目）は、実施済みかどうか確認できない【未確認】。`tests/ai/openai-live.spec.ts` は存在するが、実キーでの実行は行っていない。

### 4.2 費用の試算【推定】

コード内の上限値（画像4枚＝入力約2.7万トークン、出力上限1.6万トークン）に、`src/lib/ai/pricing.ts` の単価を掛けた最悪ケースの試算。**単価はコード内の記載で、OpenAIの公式料金で再確認していない**【未確認】。為替はコードの165円/ドル。

| 条件 | 1回の最悪ケース（標準モデル） | 同（高精度モデル） | 1期間（3ドル）あたりの回数 |
|---|---|---|---|
| 画像4枚の読み取り | 約0.011ドル（約2円） | 約0.23ドル（約38円） | 約260回／約13回 |
| 予定表100行の文字読み取り | 約0.012ドル（約2円） | 約0.25ドル（約40円） | 同程度 |
| PDF文字6,000文字の抽出 | 約0.008ドル（約1円） | 約0.17ドル（約28円） | 同程度 |

実際の消費は予約額より小さくなる設計（実使用量で精算）。高精度モデルは標準の約20倍のため、**既定を標準にして、必要なときだけ高精度**という現在の設計は、費用面で妥当【推定】。

### 4.3 AIの導入判断表

「導入」は有料AIの追加を指す。AIを使わない代替手段を先に検討した結果。

| 対象 | 判断 | 理由・代替手段・リスク |
|---|---|---|
| 領収書・請求書の画像からの項目抽出（新ツール、5項） | 条件付きで導入 | 画像送信が必要で、同意と送信内容の明示が必須。金額・日付の誤読が会計に直結するため、利用者の確認画面と二重チェック（合計＝内訳の突き合わせ）が前提。先にブラウザ内OCR＋ルールで作り、AIは「読めなかったときの補助」に限る案が安全。既存の `form-extract` の仕組みを流用でき、新しい基盤は不要 |
| `ocr` の精度向上 | 当面導入しない | 既存のTesseractで足りる用途が中心。AIが必要なのは手書き・低画質で、需要と費用が未確認。入口を作るなら `form-extract` の画像モードの再利用で足りる |
| `pdf-to-excel` の表の再構成 | 実装済み | 追加の導入は不要。精度の測定が先 |
| `pdf-to-word` | 導入しない | 変換は版面の再現問題で、AIの得意領域ではない。誤変換の検証コストも大きい |
| 名簿の列の自動対応 | 導入しない | 既に `column-mapping.ts` にルール処理がある。氏名・住所などの個人情報を外部送信してまで補う価値は低い |
| 表記ゆれ・名寄せ（`csv-dedupe` の強化） | 当面導入しない | 端末内の曖昧一致（全角半角・空白・かな）で大半を処理できる。個人情報を外部へ送る点が原則（ブラウザ内完結）と相性が悪い |
| 個人情報の検出・マスキング（新ツール） | **導入しない** | 個人情報を見つけるために個人情報を外部送信するのは矛盾する。正規表現（電話・メール・マイナンバー形式・郵便番号）と辞書による端末内処理が適切 |
| 座席づくり（新ツール） | 導入しない | 制約を満たす割り当て問題で、アルゴリズムの領域。AIは再現性と説明可能性を損なう |
| シフト表の自動作成（新ツール） | 導入しない（自然文の入力補助は将来の選択肢） | 制約充足と最適化の問題。AIの出力を人が検証するより、解の探索を端末内で行い、満たせない制約を明示するほうが安全 |
| Excelの差分・結合・整形 | 導入しない | 機械的に決まる処理。AIは誤りの検証コストが増えるだけ |
| 画像系（圧縮・変換・回転・余白など） | 導入しない | 処理は決定的で、端末内で完結 |
| 背景除去 | 実装済み（端末内） | 既に端末内の推論。外部送信は無い |
| 動画・音声・ファイル操作 | 導入しない | AIの必要性が無い |
| 年度カレンダーのAI改善 | 実装済み（重複して計画しない） | 追加するなら、精度の実測結果を見てから |

### 4.4 AIを足す前に決めておくべき共通の条件【推定】

1. AIの画面は、必ず「AIを使わない通常の結果」から始め、AIは提案として表示する（現行の方針と同じ）。
2. 送信内容の確認画面と、利用者の同意の記録を維持する（既存の仕組みを新機能にも適用）。
3. 新しいAI機能を足す前に、既存4機能の実費・精度の測定結果を揃える（現在は上限の試算しかない）。
4. AIが主役のツールを作らない。AIは通常処理の補助に留める。

### 5.3 判断が必要な点【推定】

1. AC.Satto を、別サイトのまま育てるか、Mr.Satto の1ツールとして取り込むか、Mr.Satto から案内リンクで結ぶだけにするか。取り込む利点は、サイトへの集客を共有できることと、プランや同意の仕組みを使えること。欠点は、2つのコードベースの統合に手間がかかること、OCRの重い読み込みでMr.Sattoの他ツールに影響しうること。
2. 会計ソフトに標準でレシート読み取りがあること（弥生のスマート取引取込のページが検索結果に出ることは確認したが、機能の詳細は**未確認**）を踏まえ、差別化は「ソフトを契約していない個人・小規模が、CSVだけ作る」「ファイルを外部に送らない」に置くのが現実的。
3. 5-C と 5-D は、読み取りもAIも不要で、既存の発行系ツールと同じ作り方で済む。5-A / 5-B の判断を待たずに進められる。ただし需要は【推定】にとどまり、実測は無い。
4. AI（4.3）: 領収書の項目抽出にAIを足すかは、ブラウザ内OCRの精度を先に評価してから。AC.Satto は「初期は外部AIを使わない」方針。

### 7.2 各候補の所見

**Excel差分比較**。2つのExcelの違いをセル単位で色づけし、行の追加・削除・値の変更を一覧にする。業務ファイルは機密のことが多く、「ファイルを送らない」ことが価値になる【推定】。検索結果に、オンラインの比較ツールがいくつも出る（題名のみ確認。機能・料金は**未確認**）。難しさは、行の並びが変わった場合の対応づけ（キー列の指定が必要）と、大きなファイルでの速度。

**複数Excelの結合**。`csv-merge` はCSVだけで、Excel同士・複数シートの結合は無い【事実】。列名が揃っていない名簿・台帳の統合（列の対応づけ、重複検出）は、既存の `column-mapping.ts` の考え方が使える。最も実装コストが低く、効果が見えやすい候補【推定】。

**Excelデータ整形**。既存の `excel-replace`、`excel-blank-remove`、`text-case-converter`、`csv-format` などと機能が重なる【事実】。新ツールとして足すより、既存ツールの統合や入口の整理（3-5）として扱うほうが自然【推定】。

**シフト・当番表の自動作成**。条件（希望休、必要人数、連勤の上限、資格）を満たす割り当てを探索する問題。座席表と同じ「制約を満たす端末内の探索」で、仕組みを共有できる可能性がある【推定】。ただし、シフト表は条件が事業所ごとに大きく異なり、既存のシフト管理サービスも多い（検索で競合を網羅的には調べていない／**未確認**）。座席表を先に作って探索部品を育ててから判断するのが安全。

**名札・案内状・文書の一括**。現状、封筒宛名（`envelope-address`）、ラベル（`excel-label`）、整理券（`ticket-voucher`）、フォームからの個別PDF（`form-to-individual-pdfs`）はある【事実】。無いのは「名簿＋Wordまたは自由レイアウトのひな形」から、名札・席札・案内状を一括で作る汎用の差し込み。座席表と組み合わせると席札につながる【推定】。

**PDFの抜け漏れ・不備チェック**。ページの欠落・向き違い・白紙ページ・サイズ混在・文字情報のないページ（スキャン）・暗号化などの検出。提出前の確認ツールとして成立するが、「抜け」は書類ごとの基準が違うため、汎用では価値が見えにくい【推定】。

**個人情報の検出・マスキング／確実黒塗り**。
- 現状【事実】: PDFの白消しは見た目だけで、元の文字は残る（画面とFAQで明記済み）。画像のモザイクはある。PDFの確実な黒塗り、およびExcel/CSVの個人情報の検出は無い。
- 実現方法【推定】: PDFのページを画像として描画（`pdf-render` が既にある）→ 黒塗り → 画像から新しいPDFを作る（`image-to-pdf` と同じ流れ）ことで、文字情報ごと消せる。副作用は文字検索ができなくなることとファイルが大きくなること。検出は正規表現（電話、メール、郵便番号、マイナンバー形式、カード番号形式）と辞書で端末内に行う。**AIを使わない**（4.3）。
- 検索結果には、PDFの黒塗りと個人情報のマスキングを扱うサービスが出る（題名のみ。機能は**未確認**）。
- 「白消しの限界」を自分たちで明記しているサイトの方針と一貫した、信頼を築きやすい候補。

**一括ファイル名変更の強化**。`file-bulk-rename` と `file-sequential-rename` はあるが、Excelの対応表（旧名→新名）での変更は無い【事実】（ツールの説明とコードにExcel/CSVの記述が無いことを確認）。名簿からの氏名入りファイル名づくりに使える。

**はがき・年賀状の宛名面**。`envelope-address` は長形3号・長形4号・角形2号が対象で、はがきは説明に無い【事実／未確認】。需要は11〜12月に集中する【推定】。今年の繁忙期に間に合わせるには時間が足りない可能性が高い（日付は2026-10-30）。来季向けの準備として位置づける。

## 8. ツール間のデータ引き継ぎの状況と不足

### 8.1 実装済み【事実】

| 項目 | 内容 |
|---|---|
| 仕組み | `src/lib/pdf/file-handoff.ts`。ブラウザのメモリ上に `File` を1つだけ置き、受け取り側が1回だけ取り出す |
| 保存・通信 | ネットワーク不使用。localStorage / sessionStorage / IndexedDB / Cookie / URL には保存しない |
| 期限・上限 | 15分で失効、50MBまで、宛先ツールIDが違えば受け取れない、新しい引き継ぎが古いものを置き換える |
| 引き継ぎ元 | PDF編集の6操作（結合・分割・ページ削除・並べ替え・回転・抽出）の結果に「PDF修正で開く」ボタン（`OpenInPdfFixButton`） |
| 受け取り側 | `pdf-fix`（取り出し後に形式・サイズを再検査）。`pdf-fill-annotate` は内部の `initialFile` で受ける |
| 画面内の共有 | PDF編集・PDF修正の機能切り替えでは、選んだPDFが切り替え後も保たれる（`SharedPdfFileProps`） |
| テスト | `tests/tools/pdf-fix.spec.ts`。1回だけ受け取り、宛先違い、期限切れ、置き換え、形式・サイズ検査、上限ちょうど／超過、再読み込みで残らない、通信・保存が無いこと、編集中の切り替え確認、など単体・画面の両方 |

結論: 「PDF編集 → PDF修正」の引き継ぎは**実装済みで、テストも手厚い**。作り直す必要は無い。

### 8.2 未実装（不足）【事実＋推定】

| 流れ | 現状【事実】 | 不足による手間【推定】 |
|---|---|---|
| 画像ツール同士（リサイズ→圧縮→形式変換→PDF化／結合など） | 引き継ぎなし。各ツールでダウンロードして選び直す | 画像は連続して使う場面が多く、効果が大きい |
| 画像 → PDF | 引き継ぎなし | 同上 |
| PDF → 画像／OCR／テキスト／Excel | 引き継ぎなし（PDF修正への引き継ぎ以外は無い） | スキャンPDFの「OCRしてExcelへ」などの連続処理 |
| PDF → Excel → CSV整形・Excel加工 | 引き継ぎなし | 変換後に整形する流れが典型 |
| 名簿（Excel/CSV）→ 封筒・ラベル・整理券・名簿テンプレート・個別PDF | 各ツールが個別に読み込み | 同じ名簿を毎回選び直す。将来の座席表・名札にも関わる |
| PDF修正の結果 → ほかのPDFツール（圧縮・透かし等） | 引き継ぎなし（PDF編集→PDF修正の一方向のみ） | 逆方向や圧縮への流れが無い |

### 8.3 設計上の観点【推定】

- `file-handoff.ts` は名前もPDF専用だが、実体は「File＋宛先ID＋期限」の小さな受け渡し口。画像や名簿にも同じ方式（メモリのみ・1回だけ・宛先指定・期限）を一般化できる可能性が高い。ただし、名前の変更や型の一般化は、既存の引き継ぎとテストへの影響があるため、独立した工程にする。
- 引き継ぐ内容の候補は、(a) 処理結果のファイル（PDF・画像）と、(b) 名簿のような「解析済みの表」の2種類。表は、再解析を省ける反面、列の対応づけの設定の持ち越しも検討になる。
- 設定（品質、サイズなど）は引き継がない、というのが現行の考え方。ツールごとに適切な既定値があるため、今のところ妥当と考える【推定】。
- 保持の方針: 現行と同じメモリのみ・短時間・1回限りを維持する。ブラウザの保存領域への書き込みは、プライバシーポリシーの記述と矛盾するため行わない。

### 10.2 推奨する順序【推定】

評価（7.1）と、原則（ブラウザ内完結、データを残さない、サーバー費用を増やさない）に基づく Claude の案。最終判断は本人。

1. **根拠づくり（D1）**: 実装なしで先に実施できる。Search Consoleの確認結果があれば、候補の順位づけが推定から実測に近づく。
2. **Excel結合・差分比較**（まとめて「Excel名簿・台帳の統合と比較」）: 実装コストが低〜中で、需要が見込め、プライバシー訴求が強い。名簿を扱う部品の土台にもなる。
3. **PDFの確実黒塗り＋個人情報の検出**: 「白消しの限界」を解消し、サイトの信頼にも合う。新しい基盤が要らない。
4. **座席表（テーブル割り）の最小版**: 差別化は大きいが実装は重いので、2・3で名簿と制約の部品を整えてから着手する。結婚式向けの体裁は含めない。
5. **経理系**: D2を決めた後。5-C（経費精算書）・5-D（領収書作成）は軽いため、前倒しも可能。
6. **名簿・画像の引き継ぎ基盤**: 新ツールの数が増えた段階で効果が大きい。D6の判断による。
7. **シフト表**: 座席表の探索部品の評価後に判断する。

並行して小さく進められるもの: HEICの確認（D5）、`image-compress` など上位ツールの説明文・FAQの強化。
